# Android port — plan

## Goal

Ship Local PDF Organizer as an Android app with the same five tools, built from this repo with
Tauri 2's Android target. One codebase: the Rust core and the React UI are reused; only the platform
edges differ. Desktop must keep working unchanged.

Test device: arm64-v8a phone, Android 16 (API 36), 1268×2756 portrait.

## Architecture decisions (set by the lead; do not relitigate, raise concerns under RISKS)

1. **Tauri 2 Android**, not a separate native app. `src-tauri/gen/android` is generated by
   `tauri android init` and committed.
2. **PDFium on Android** = prebuilt `libpdfium.so` from `bblanchon/pdfium-binaries`
   (`pdfium-android-arm64.tgz`, plus `arm`/`x64` if cheap), placed in the app's `jniLibs/<abi>/` so the
   system linker finds it by name. Same release tag family as the bundled Windows `pdfium.dll`.
3. **Files in, files out.** Android pickers return `content://` URIs, which `std::fs` cannot open.
   - **Import**: every picked file is copied into the app cache (`<cache>/imports/<uuid>/<name>`) and
     the existing pipeline works on that real path. The display name comes from the URI.
   - **Export**: every tool writes its result to `<cache>/exports/…` first. The user then chooses
     **Save to…** (system "create document" picker) or **Share** (Android share sheet). No tool needs
     a writable public folder.
   - Multi-file results (PDF → images without ZIP, multi-file compress) are saved through the same
     export step; when a single destination is required they are zipped.
   The exact plugin APIs are decided in `docs/android/RESEARCH.md`.
4. **One platform seam per side.**
   - Frontend: `src/shared/platform/` exposes `isMobile`, and the file helpers
     (`pickFiles`, save/share of results). Tool pages call these helpers and never branch on platform
     themselves beyond what the helper returns.
   - Backend: `src-tauri/src/core/platform/` holds the import/export code. Feature services stay
     platform-agnostic (they keep receiving real paths).
5. **Mobile UI = same pages, responsive.** Below the `lg` breakpoint: bottom navigation, the tool
   sidebar becomes a sticky bottom action bar with an options sheet, touch-first controls (no hover),
   long-press to drag, pinch/swipe in the viewer, safe-area insets.

## Phases

| Phase | Work | Owner role |
|---|---|---|
| 1a | Research: exact Android APIs for dialog/fs/opener/share, PDFium loading | Researcher |
| 1b | Toolchain, `tauri android init`, PDFium `.so`, first APK that boots | Platform engineer |
| 1c | Responsive shell and layout | Mobile UI engineer A |
| 1d | Touch interactions, tiles, viewer gestures | Mobile UI engineer B |
| 2  | Import/export seam (Rust + TS), tool pages wired to it | File I/O engineer |
| 3  | Integration build, on-device test, fixes | Platform engineer + lead |
| 4  | Independent review, docs | Reviewer |

## Definition of done

- `npm run build`, `npm run lint:deps`, `cargo test` (desktop) all green.
- A debug APK installs on the test phone, opens, and all five tools complete a real job:
  pick → arrange → run → save or share → file opens in another app.
- Desktop build and behavior unchanged.
